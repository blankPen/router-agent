03

分派设计：事件分给谁、依据什么、怎么收口

这是上一版最没想清楚的部分。核心结论：不新造 worker 类型，分派 = 「选剧本 + 选运行时 + 定授权范围」，执行仍然交给现有 Worker。

事件出队 · 判定通过↓
① 匹配剧本 Playbook↓ 类型精确 > 标签 > 来源默认 > 通用兜底
特化剧本（点对点）
github-bug-triage

固定 SOP：拉取 issue 上下文 → 复现与定位 → 产出根因与修复计划。跳过澄清，直接进计划阶段。

例子：已注册的 issue / PR / CI / 定时巡检
通用剧本（澄清优先）
generic-intake

先做需求分析与澄清，产出明确执行方案后再执行。未注册类型默认走这条。

例子：http 注入的未知事件、运营群转来的事件
审核剧本
human-gate

缺关键信息、或命中风险清单（安全 / 生产 / 付费 / 对外发布）时，不执行，直接进待审核。

例子：无法定位项目、影响生产的告警
② 澄清策略三档（仅通用剧本需要）
自动澄清
信息足够 → 直接执行

从事件上下文（标题、正文、标签、仓库、作者）自动补齐项目、分支、复现信息。

置信度高
带假设执行
信息不全 → 标注假设

Plan 里写明假设与影响范围，执行后回报中同时给出假设，便于复核。

置信度中等
转人工
缺关键项 → 待审核

不阻塞在队列里等人对话，直接进待审核队列 + 飞书卡片通知 admin。

置信度低 / 高风险
③ 选目标 Worker：按能力匹配现有运行时↓
④ 生成任务包 → 开单 → 复用 launch() 派工 → Worker 执行↓
⑤ 回写事件：状态、结论、关联工单 / PR、成本
取舍「每类事件一套固定 worker」与「所有事件统一澄清再执行」不是二选一：统一澄清再执行是骨架（保证任何事件都有可执行方案再动手），点对点剧本是特例（已注册类型跳过澄清走固定 SOP）。特例仍复用同一条澄清/计划/执行代码路径，不会出现两套逻辑漂移。
04

剧本（Playbook）是什么

剧本是一份声明式配置，回答「这类事件该怎么处理」。它不是新进程、不是新 Worker 类型，只是给现有 Worker 换一套判定问题、提示词与工具范围。

特化剧本
github-bug-triage
匹配sourceType=github-issue ∧ labels∋bug
澄清跳过（用 issue 上下文自动补齐）
产物复现路径 + 根因 + 修复计划
运行时按 capability 选（默认 codex）
工具范围只读 + 可写代码仓（不含生产）
审核命中安全标签则强制审核
特化剧本
ci-failure-followup
匹配eventType=ci.failed
澄清跳过
产物失败归因 + 是否重跑
运行时轻量运行时（只读日志）
工具范围只读
审核否
特化剧本

匹配sourceType=schedule
澄清跳过
产物日报 / 巡检报告
运行时轻量运行时

审核否
通用剧本（兜底）
generic-intake

澄清自动澄清 → 带假设 → 转人工

优先级 P0–P4：四象限 + 噪声

按「重要 / 紧急」四象限划分，由 Jev 一次判定给出；P4 单独留给明确无效的噪声事件，直接忽略。

象限
紧急
不紧急
P0
重要且紧急
立刻执行 · 可插队 · 全天窗口
P1
重要不紧急
必须做 · 排期执行 · 低峰批量
—
P2
紧急不重要
快处理但低成本 · 低优运行时 · 合并执行
P3
不重要不紧急
仅记录 · 不自动执行 · 面板可见
—
P4
明确无效 / 噪声
直接忽略 · 保留审计记录
为什么多一档四象限只能表达「要不要做」，表达不了「明确是噪声」。「P4 无效」把噪声与「低价值但有效」区分开：P3 保留记录可回溯，P4 直接丢弃，二者都不占用执行预算。
06

事件队列状态

四类业务状态（无效 / 待处理 / 已处理完成 / 待审核）为主，另有三个执行态用于重试与延后，不打乱业务分类。

订阅接入→ P4 无效事件｜ 待处理→ 待审核→ 已处理完成 执行态：延后 / 重试中 / 失败
状态含义下一步
无效事件判定为噪声或与项目无关归档保留，可回溯为什么没处理
待处理已判定该做，等待执行按优先级 + 窗口出队 → 澄清/计划 → 派工
待审核需要人介入才能继续飞书卡片 + 面板红点；批准 → 回到待处理
已处理完成Worker 已执行并回报回写来源（Issue 评论 / 回调 / 通知），关联工单与 PR
执行态延后（窗口外）、重试中、失败仍属于「待处理」的子状态，超限转「待审核」
