事件流程方案：两条路，同一个 Worker

左边是飞书消息：用户说话，系统听完派活；右边是事件：系统自己收到事，判断要不要做、什么时候做、派给谁。两路最后都变成一张工单，交给同一批 Worker。

工单 tk-87 版本 v3 · 简化版 飞书流程 不动 事件优先级 P0–P4 本轮 只出设计

路 B 细看：事件怎么变成活

这条链路是本方案新增的核心。和路 A 最大的不同：中间没有对话，所以「补信息」要靠自动或转人工。

1
订阅器接到
GitHub 轮询/订阅、HTTP 注入、定时任务触发
插件可扩展
2
归一 + 排队
统一成事件信封，重复的合并，按优先级排队
3
判断一次
要不要做？多急？什么类型？要不要人审？
规则先判，模型兜底
4
选处理方式
匹配剧本：这类型事件按哪套流程走
4b · 分支
补不齐时转人工
只在缺关键信息或高风险时走：进待审核队列，等 admin 拍板
排队等人，不阻塞
5
出方案
补齐信息，产出可执行方案（假设要写明）
6
开单派工
和路 A 一样：生成工单 → 派给 Worker
7
回写
状态、结论、关联工单写回来源
没有对话怎么办事件不等人回答。三档处理：信息够 → 直接办；信息不全但能猜 → 带着假设办并写明假设；关键项缺失或命中风险清单（安全 / 生产 / 付费 / 对外发布）→ 进待审核队列，不执行。
04

事件分给谁：三个问题

分派不是写一堆 if-else，而是「先选处理方式，再选执行者」。

事件出队 · 判断通过↓
① 这类事件该怎么处理？↓ 先找特化方式，找不到用通用方式
特化方式
已注册的类型

这类事件有固定套路，直接按套路走，不做多余的澄清。

例：GitHub bug、CI 失败、定时巡检
通用方式
没注册的类型

先自动补信息、出方案，再执行。任何事件都有出路。

例：HTTP 注入的未知事件
转人工
缺关键信息 / 高风险

不执行，直接进待审核 + 飞书卡片通知 admin。

例：定位不到项目、影响生产
② 信息够不够？↓ 够 → 办；不够但能猜 → 带假设办；不够且关键 → 转人工
③ 派给谁执行？↓ 按能力选现有运行时
④ 开单 → 派工 → Worker 执行 → 回写事件
能力要做什么典型执行者
只读看代码、看日志、读监控轻量运行时（只读模式）
改代码写代码、跑测试Codex / Claude Code
仓库操作建分支、开 PROrca（worktree + PR）
重要取舍「每类事件一套固定 worker」和「所有事件统一澄清再执行」不是二选一：统一澄清再执行是骨架（保证任何事件都是「有方案才动手」），固定流程是特例（已注册的类型跳过澄清走固定套路）。而且不为每类事件新造 Worker 类型 —— 差别只在判定问题、提示词、工具范围、目标运行时这四处，写成配置即可。
05

事件、工单、项目：三者什么关系

项目是「在哪干活」，工单是「要干的活」，事件是「为什么开始干」。事件本身不预绑项目 —— 项目是派工前解析出来的。

事件
刚进来的时候，它只有来源、类型、优先级、正文
还没有项目 —— 项目要等派工前才解析
↓ 派工前解析项目（拿不到就转人工，不阻塞）
项目解析链
按可信度依次找，找到就用
① 订阅器写明的仓库› ② 剧本声明的默认项目› ③ 事件内容里提到的项目名› ④ 全局只有一个项目› ⑤ 都没有 → 转人工
解析结果会回填到事件上：事件始终带着「它落到哪个项目」，面板和工单页都能看到。
↓
出路 A · 新开一张工单
项目 → 工单 → Worker
  • 工单绑定项目：仓库 + 分支 + 运行时
  • Worker 就在这个项目的 worktree 里干活
  • 和飞书消息开的工单完全一样
出路 B · 投给已有的工单
不新开单，作为「输入」投递
  • 事件和某张在办工单相关时（同一个 Issue 的后续评论）
  • 把事件内容投进那张单，不重复建单
  • 工单上能看到「又来了一条事件」

07

事件队列：四种状态

事件进来后只有四种归宿。

待处理→ 待审核→ 已处理完成 无效事件（忽略，但留记录）
状态什么意思接下来
待处理判断过了，该做，在排队按优先级和时段出队 → 补信息 → 派工
待审核需要人拍板才能继续飞书卡片 + 面板红点；批准后回到待处理
已处理完成Worker 做完了结论回写来源，关联工单与 PR
无效事件噪声、重复、与项目无关归档留痕，面板可查「为什么没处理」
