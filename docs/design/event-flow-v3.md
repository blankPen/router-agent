# router-agent 事件流程方案（v3 · 简化版）

> 一页看懂：**两条路，同一个 Worker**。飞书消息那条路保持现状不动；事件这条路是新增的。
> 本版按反馈重写：多画流程图、少讲实现。

---

## 0. 一句话说明

- **路 A · 飞书消息**：有人说话 → 系统听完 → 派活 → Worker → 回话。**有对话**，缺信息可以追问，用户在等。
- **路 B · 事件**：系统自己收到事 → 判断要不要做、什么时候做、派给谁 → Worker → 回写来源。**没有对话**，缺信息只能自动补齐或转人工。

两路的终点相同：都变成一张工单（带授权范围、仓库、分支），交给同一批 Worker。所以事件这条路**不重写执行链路**，只新增「订阅 → 判断 → 选处理方式」三段。

![一图看两条路](@./docs/design/figures/fig-v3-routes.png)

## 1. 路 A：飞书消息（保持现状）

这一路已经跑得很顺，方案里原样保留：

![路 A：消息怎么变成活](@./docs/design/figures/fig-v3-channel.png)

要点：
- **准入判断不花钱**：机器人消息、纯寒暄直接丢掉，不进模型。
- **需求分析靠对话**：缺项目、缺分支、缺复现信息，追问补齐。
- **管理员终审后才开单**：开单时同时写下授权范围，Worker 照着做。

---

## 2. 路 B：事件（新增）

![路 B：事件怎么变成活](@./docs/design/figures/fig-v3-event.png)

与路 A 最大的不同：**中间没有对话**。事件不等人回答，所以「补信息」只能靠自动补齐，或者转人工。

- **补齐分三档**：信息够 → 直接办；信息不全但能猜 → 带着假设办，并在回报里写明假设；关键项缺失或命中风险清单（安全 / 生产 / 付费 / 对外发布）→ 进待审核队列，**排队等人，不阻塞**。
- **规则先判、模型兜底**：规则能定案的完全不调模型；模型只在灰区调一次（要不要做？多急？什么类型？要不要人审？）。
- **事件必须有回写通道**：订阅器要声明结论怎么回去（Issue 评论 / HTTP 回调 / 飞书卡片）。没有回写能力的事件只落库，面板里能看到，但不会假装「做完了」。

## 3. 事件分给谁：三个问题

![事件分派：三个问题](@./docs/design/figures/fig-v3-dispatch.png)

| 问题 | 答案 |
| --- | --- |
| **这类事件该怎么处理？** | 先找「特化方式」（已注册的类型，有固定套路）；找不到就用「通用方式」（自动补信息 → 出方案 → 执行）；缺关键信息或高风险 → 转人工 |
| **信息够不够？** | 够 → 办；不够但能猜 → 带假设办；关键项缺 → 转人工 |
| **派给谁执行？** | 按能力从现有运行时里选：只读 / 改代码 / 仓库操作，不为事件新造 Worker 类型 |

**关于你提的两个方案**，结论是：**统一澄清再执行是骨架，固定流程是特例**。

- 事件类型不可能穷举，所以必须有一条通用出路（骨架）：任何事件都是「有方案才动手」。
- 已注册的高频类型（GitHub bug、CI 失败、定时巡检）走特化方式，跳过多余的澄清（特例）。
- 特例不是新代码，也不是新 Worker 类型 —— 差别只在「判定问题、提示词、工具范围、目标运行时」这四处，写成配置就行（叫「剧本」）。

## 4. 优先级：什么先做

![优先级 P0–P4](@./docs/design/figures/fig-v3-priority.png)

| 级别 | 含义 | 怎么排 |
| --- | --- | --- |
| P0 | 重要且紧急 | 立刻做，可插队，全天都做 |
| P1 | 重要不紧急 | 排期做，低峰批量做 |
| P2 | 紧急不重要 | 用低成本的执行者，合并着做 |
| P3 | 不重要不紧急 | 只记录，不自动做 |
| P4 | 明确无效（噪声、重复、与项目无关） | 忽略，但留审计记录 |

P3 和 P4 都不占执行预算，区别是 P3 还算「有效事件」、P4 是「根本不该进来」。

---

## 5. 事件队列：四种状态

![事件队列四种状态](@./docs/design/figures/fig-v3-queue.png)

- **待处理**：判断过了，该做，在排队。
- **待审核**：需要人拍板（批准 / 驳回 / 延后），批准后回到待处理。
- **已处理完成**：Worker 做完了，结论回写来源。
- **无效事件**：忽略，但留记录，面板可查「为什么没处理」。

## 6. 配置界面要配什么

### 6.1 事件订阅页：卡片 + 设置弹窗 + 添加自定义插件

![配置界面（一）：事件订阅](@./docs/design/figures/fig-v3-config-sub.png)

- 每个订阅器一张卡片，显示状态和关键配置摘要；点「设置」弹窗配该订阅器自己的字段（字段由插件自己声明，宿主不写死）。
- 「＋ 添加自定义插件」可以装第三方 npm 事件源包，机制与现有的 runtime 插件一致。
- 订阅器加载失败只标记自己不可用，不影响其它订阅器。

各订阅器要配的东西：

| 订阅器 | 要配什么 | 备注 |
| --- | --- | --- |
| **GitHub** | 仓库、接入方式（轮询 / 订阅）、轮询间隔、监听哪些事件（issue / PR / CI）、标签白名单、默认优先级、每日配额 | 轮询先上，订阅留二期 |
| **HTTP 事件** | 接口路径、密钥、限流（每分钟条数）、允许的事件类型 | 外部系统注入事件的入口；密钥用于验签，防重放 |
| **飞书消息订阅** | 本期占位，只留开关 | 二期再做规则检测 |
| **自定义插件** | npm 包名 + 该插件声明的字段 | 装不上只提示，不影响其它订阅器 |

### 6.2 处理方式（剧本）配置：这类事件该怎么处理

![配置界面（二）：处理方式与队列](@./docs/design/figures/fig-v3-config-playbook.png)

一条规则 = 一类事件的处理办法，要配的就这 8 项：

| 配什么 | 说明 | 例子 |
| --- | --- | --- |
| 适用事件 | 什么情况下用这条规则 | GitHub Issue 且带 bug 标签 |
| 处理办法 | 这类事件的固定套路 | 复现 → 定位 → 出根因与修复方案 |
| 要不要澄清 | 跳过 / 自动补齐 / 转人工 | 跳过（信息从 issue 自动取） |
| 执行者 | 按能力选现有运行时 | 能改代码的（默认 Codex） |
| 权限范围 | 允许做到哪 | 可改本仓库代码，不碰生产 |
| 审核 | 什么情况必须人工审 | 带 security 标签时 |
| 预算与时段 | 单条上限、什么时候跑 | 单条 6 万 token，低峰执行 |
| 结果回写 | 结论怎么回来源 | 在 Issue 下留言 |

### 6.3 全局策略配置：影响所有事件

| 配什么 | 例子 |
| --- | --- |
| 高峰时段 | 09:00–20:00，只做 P0 / P1 |
| 低峰时段 | 20:00–09:00，批量做 P2 / P3 |
| 每日 token 上限 | 20 万（超了低优事件顺延，不丢） |
| 单来源上限 | 每个来源每天 50 条 / 单独配额 |
| 审核通知 | 飞书卡片发给 admin；P2 合并成一张 |
| 回写要求 | 没有回写通道的事件只落库、不标记完成 |
| 插件来源白名单 | 允许安装哪些 npm 包 |

### 6.4 事件队列页

- 按优先级分栏：P0 置顶，其余按优先级和等待时长排序；每条显示来源、判断理由、当前处理方式、已等待多久。
- 能做的操作：提升 / 降级优先级、立即执行、忽略、合并同类事件。
- 待审核单独一块，批准 / 驳回 / 延后；处理过的不再重复通知。

## 7. 成本与时段

![成本与时段](@./docs/design/figures/fig-v3-cost.png)

- **时段**：高峰期只做重要的事，低峰期批量做低优任务；窗口可以在面板临时改，改完立即生效。
- **三档预算**：单条事件、单个来源、全局。超了统一**顺延**（不是丢弃），P0 不受影响。
- **省 token 的大头不是把提示词写短，而是规则先判、模型兜底**，加上低峰期把同类事件合并成一次判断。

---

## 8. 落地节奏

| 阶段 | 做什么 | 做完的标志 |
| --- | --- | --- |
| 一期 | 事件骨架：订阅插件机制、GitHub / HTTP 订阅器、队列、面板只读 | Issue 能进队列并在面板看到判断结论；HTTP 能注入一条事件并跑完一次派工 |
| 二期 | 分派与剧本：剧本注册、通用剧本、任务包、结果回写 | 不同类型事件自动走不同处理方式；带假设执行的会标注；结论能回写到 Issue |
| 三期 | 审核与界面：待审核列表 + 卡片通知、订阅卡片与设置弹窗、自定义插件安装 | admin 能在卡片或面板完成批准 / 驳回；能装一个第三方事件源插件 |
| 四期 | 成本与时段：时间窗口、预算、降级、成本统计 | 高峰只跑 P0/P1；超预算自动顺延且不丢事件；面板能看到今日成本 |

---

## 9. 已确认与待拍板

**已确认**
- 优先级保留 P0–P4 五档，P4 专门留给明确无效的事件。
- 分派采用「通用方式为骨架、特化方式为特例」，不为事件新造 Worker 类型。
- 飞书 channel 流程不动，两条路只在派工处汇合。
- 队列四类状态 + 延后 / 重试 / 失败三个执行态。

**待拍板**
- 高峰 / 低峰的时段与预算默认值（文档里用的是 09:00–20:00 / 20 万 token，可直接改）。
- GitHub 订阅先上轮询还是直接上订阅（建议先轮询，二期再上订阅）。
