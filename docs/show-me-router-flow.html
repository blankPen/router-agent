router-agent · 流程解剖

一条飞书消息，
如何走到 PR 闭环

这份图基于仓库真实代码绘制：飞书消息经 lark-cli 事件流进入 Router， 由确定性 Gate + LLM 研判决定接不接单，接了就派一个 Orca worktree 里的 Worker， Worker 只写 state.json 上报，Router 轮询后把进展回复到原话题。

1s 主循环 8s 消息聚合窗口 4 并发 worker 上限 5s PR 跟踪 15s 空闲巡检
01

全景：九个环节

一次完整的消息生命周期。颜色代表消息/状态所在的组件。

01飞书消息用户 @bot / 私聊
02事件流lark-cli consume
03归一化Trigger
04入库SQLite state.db
05Gate + 研判规则 → LLM
06开单Ticket / Mandate
07派工orca worktree
08执行 + 上报state.json
09通知 / 闭环飞书话题 + PR
核心约束 所有状态写入只经过 Engine（src/core/engine.ts）；所有出站消息先进 outbox 再由 Effects 幂等发送。 Router 不直接操作 SQLite，也不解析终端屏幕文本。
02

端到端时序

从「用户按下回车」到「工单闭环」。左侧数字是执行顺序，不是严格耗时。

1
飞书事件到达飞书

常驻子进程执行 lark-cli event consume im.message.receive_v1 --as bot，stdout 按 NDJSON 一行一个事件。 stdin 必须保持打开的管道——lark-cli 把 stdin EOF 当作退出信号。

src/sources/feishu.ts · FeishuConsumer.start()
2
归一化 + 过滤Router

依次判定：群是否在监听范围 → 是否机器人自己发的（防自激）→ 只接 @ 的群里有没有 @ 到 bot → 内容是否为空。 通过则生成 Trigger：threadId = feishu:{chatId}:{rootId}， addressed = mention | direct | none。

被丢弃的消息写一条 trigger:dropped 日志并附原因——否则用户只会看到「没反应」。

src/sources/feishu.ts · normalizeFeishuEventDetailed()
3
入库 + 回执表情SQLite飞书

engine.ingest() 幂等写 Trigger（同一 message_id 只进一次），同时 upsert 线程记录。 对「在跟它说话」的消息立刻加一个 Typing 表情，先把「收到了」的反馈给到人。

回复真正发出时，再按 originMessageId 撤销这个表情。

src/cli/index.ts · onEvent / reactTo / clearReaction
4
主循环领取Router

服务每 1 秒跑一次 runOnce()，用 ticking 标志保证周期串行不重叠。 领取条件是消息已存在超过 8 秒（聚合窗口，让人可以连发几条）， 并把 disposition 从 pending 原子改成 evaluating，防止重复处理。

src/router/agent-loop.ts · tick() / src/store/db.ts · claimPendingTriggers()
5
Gate：不花模型的第一层路由确定性

只看三件事：发送人在不在名单 × 有没有 @ / 私聊 × acceptMode，得出四种结果： explicit（显式授权）、infer（推断候选）、reply-only（策略关闭，只回一句）、ignore。

机器人消息永远不会构成显式请求；私聊也只算推断候选，只有 @ 才是显式授权。

src/core/policy.ts · gate()
6
这个线程已有工单？先扇出，不研判分支

若该 threadId 已订阅到未关闭的工单，消息直接作为 followup 投给 Worker， 跳过 Gate 与 LLM。这是「追问已有工单」的快速通道，详见第 3 节。

src/router/agent-loop.ts · hasLiveSubscription() / src/core/engine.ts · fanOut()
7
LLM 研判LLM

上下文包含：当前策略、最近 10 条线程消息、该线程已有工单。模型最多 3 轮工具调用， 最终调用 router_decide 给出 accept / ignore / stop / unavailable。

纯寒暄（你好 / 在吗 / 谢谢 / test 等整句）走规则短路，不再研判，直接用 conversation.md 生成一句礼貌回复。

src/router/agent-loop.ts · assess() / isSmallTalk() / converse()
8
落库：Decision + Mandate + TicketSQLite

engine.decide() 写一条 Decision，接单时同时创建授权书 Mandate 与工单 Ticket，并订阅该线程。 observe 模式下，推断候选的 accept 会被降级成 ignore，但记 wouldAccept=true 供人查看。

src/core/engine.ts · decide() · src/core/policy.ts · negotiateAcceptance()
9
回 ack，并开一个话题飞书

两条出站消息进入 outbox：一条普通消息「已创建工单」，一条话题回复「后续进展会在这个话题里更新」。 outbox 用幂等 key，同一个 key 不会发两次。

发出侧按 threadId 是否为空分流：空 → im +messages-send；有值 → im +messages-reply --reply-in-thread。

src/router/agent-loop.ts · reply() · src/service.ts · createEffectsSender()
10
派工：起一个 Orca worktreeOrca

同一轮循环里的 launchPending() 扫描 accepted 阶段的工单，受 maxWorkers = 4 约束。 每次派工：engine.startAssignment() → orca worktree create（新分支 + 终端 + 注入 worker 手册）→ 写 meta.json。

src/service.ts · launchPending() / launch() · src/worker/orca/index.ts · start()
11
Worker 干活Worker

在独立 worktree 里读代码、改代码、跑测试、开 PR（分支 ra/{ticketId}）。 它不发飞书、不联系发起人，每轮结束前把结果写进 ~/.router-agent/workers/{ticketId}/state.json。

src/worker/spec/prompt-mode.md · 状态上报协议
12
轮询上报 → 回话题Router飞书

每秒扫描 workers/*/state.json，按 mtime + 内容 指纹去重。 engine.report() 落报告、ack 输入、重算阶段； blocked 与 ready 会通过 outbox 回复到原话题（同一条消息只通知一次）。

src/worker/orca/report-poller.ts · scan() · src/service.ts · onWorkerState()
13
PR 跟踪与闭环GitHub

每 5 秒从两个来源找 PR：Orca worktree 自带的 linkedPR / linkedGitLabMR，或 gh pr view 兜底。 PR 变成 merged / closed 时，closeTicket() 关单并在话题里通知「工单闭环」。

src/service.ts · trackPullRequests()
03

Router ⟷ Worker 怎么交互

不是 RPC，是两条单向管道：Router 往下发命令，Worker 往上写文件。中间没有回调，也没有共享内存。

Router（编排层）

src/service.ts · src/worker/orca
  • 派工 — 起 worktree，注入整套 worker 手册 orca worktree create --repo … --name ra-tk-<编号> --branch ra/tk-<编号>-<语义>
  • 追加输入 — 把新消息作为文本敲进终端 orca terminal send <handle> "…"
  • 探活 — 长时间无输出时发一句 status? orca terminal list → lastOutputAt 结构化字段
  • 停止 — 人点停单时关终端 orca terminal close <handle>
命令 ▼ terminal / worktree
上报 ▲ state.json 文件

Worker（执行层）

Orca worktree · Claude Code
  • state.json — 唯一对外通道，每轮必须更新 state / summary / human_action / pr_* / acked_inputs
  • meta.json — Router 派工时写的身份映射 ticketId ↔ assignmentId ↔ handle ↔ workdir
  • events.log — 可选审计流水，一行一个 JSON，不参与状态机
  • PR — 自建分支 ra/tk-<编号>-<语义>，开 PR 后把编号写回 state.json；不自己合并
为什么这么设计 Router 只消费结构化字段（Orca 的 connected / writable / orphaned / lastOutputAt 与 state.json）， 从不解析终端 TUI 文本。重启后靠 recover() 与 Orca 对账：connected=false 才判定终端死亡并重新派工； orphaned=true 但可写时仍然复用。
04

Worker 的六种状态，落成什么阶段

阶段由「工单 + 派工 + 最新报告 + 是否在等人」推导，不是 Worker 直接写的。

state.json推导出的 Ticket stage会通知人吗含义
progressrunning否这轮在做，summary 说明做了什么
waitingidle否没有可做的活，不空转
blockedperson是（话题回复）要人回答，human_action 写清要做什么
failedperson否本轮失败，需人工介入
droppedidle否主动放弃，等新输入
readyreview是（话题回复 + PR 链接）PR 已开，等人 review
accepted→ assigned→ running→ review→ closed person idle ← 可从任意活跃阶段进入，也可回到 running

PR 仍处于 open 时拒绝关单，避免「代码没合就闭环」。人工停单是唯一能绕过这条限制的路径。

05

Worker 正在干活，用户又发了一条

关键区别只有一个：这条消息是不是落在已经订阅的线程里。是 → 直接塞给 Worker；不是 → 重新走研判。

情况 A · 最常见

在话题里追问
「顺便把日志也改一下」

同一 threadId，已有未关闭工单 → 跳过 Gate 和 LLM，直接作为 followup 输入投给正在跑的 Worker。

消息 → tick（8s 窗口）
→ hasLiveSubscription
→ fanOut → inputs 表
→ terminal send
→ Worker 读到并干活
情况 B · 群里另起一条

新消息、新线程
「再帮我查个接口」

没有订阅记录 → 走完整 Gate + 研判。接单则开新工单、派新 Worker，并受 4 个并发上限约束。

新消息 → 新 threadId
→ Gate → LLM 研判
→ 新 Ticket
→ 有余量就派工
→ 否则停在 accepted 排队
情况 C · 兜底

消息发了但 Worker 没反应

已投递、未 ack 的输入会在下一轮重新投递；连续无输出还会被主动唤醒，仍无响应则标记 stale 并通知人。

→ unacked 重投
→ 2 分钟无输出发 status?
→ 再 5 分钟 → stale
→ 话题里提醒人工确认
幂等细节 每条输入在库里有唯一 seq，投递 id 为 {assignmentId}:{seq}。 Worker 在 state.json 的 acked_inputs 里回写读过的 id，Router 才把状态从 delivered 改成 acked； 没 ack 的会在下一次唤醒时连同新输入一起重发——所以既不会丢，也不会因为重发而重复执行。
06

回复是怎么发出去的

Router 从不直接调飞书 API，所有出站消息统一走 outbox。

A
入 outboxSQLite

enqueueOutbox() 写入：channelKind、channelId（群）、threadId（空 = 普通消息，有值 = 话题回复）、 文本、幂等 key、以及 originMessageId（用于回执表情撤销）。

B
Effects 每秒发送飞书

单条失败只影响自己：错误写入 last_error，按退避重试，不影响同批其它消息。 成功的消息写 outbox:sent 事件，可在 ra logs --follow 里追踪。

C
通道分流路由

ack / 寒暄回复走普通消息；工单进展、blocked、ready、PR 闭环走原消息话题回复。 这样群里只有一条「已开单」，其余进展都收在话题里，不刷屏。
